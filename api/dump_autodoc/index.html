Dump — Autodoc¶

Documentación generada automáticamente desde los docstrings del módulo util_bbdd.dump. Para la referencia técnica curada con diagramas y contratos detallados, ver Orquestador y Generador de Reportes.

DumpOrchestrator¶

Orquesta el volcado completo en 7 fases: introspección → análisis FK → gestión de constraints → limpieza → carga → rehabilitación → informe Excel.

DumpOrchestrator(config) ¶

Orquesta el volcado de datos de un esquema/base de datos a otro.

Ejemplo::

from sqlalchemy import create_engine
from util_bbdd.dump import DumpConfig, DumpOrchestrator

config = DumpConfig(
    source_engine=create_engine("postgresql+psycopg2://..."),
    target_engine=create_engine("mssql+pymssql://..."),
    source_schema="public",
    target_schema="dbo",
    output_dir=Path("reports"),
    truncate_target=True,  # vaciar el destino antes de cargar; por defecto (5.0.0) no se vacía
)
result = DumpOrchestrator(config).run()
print(result.report)

run(*, on_progress=None, cancel_token=None) ¶

Ejecuta el volcado completo y retorna el resultado con el informe.

Progreso y cancelación (G1 de util_bbdd_web, 4.4.0), con el contrato de :mod:util_bbdd.progress, operación "dump": fase "tables" (un evento 0 de N al empezar la carga y uno por tabla terminada, con su nombre) y fase "rows" (uno por lote escrito de cada tabla: filas escritas de la tabla, total del COUNT(*) del origen o None sin collect_row_counts). La cancelación se comprueba antes de desactivar constraints, antes de cada tabla y entre lotes; lanza OperationCancelledError después de reconstruir los índices y reactivar las constraints. La tabla en curso se deshace (salvo los lotes ya confirmados con commit_every_n_chunks); las terminadas quedan cargadas. Con parallel_pk_ranges la carga de una tabla por rangos no se interrumpe a mitad: se comprueba antes de la tabla y no emite eventos "rows". Una cancelación que llega tras el último lote de la última tabla no interrumpe nada: el volcado termina con normalidad.

Con DumpConfig.audit_sink, escribe en él el evento de cada tabla al terminar su carga (4.4.0; antes, todos al final) y, al terminar (también si falla), los de las tablas sin destino, constraints, índices y contadores PK y un run de cierre, con el run_id del volcado (DumpResult.audit_run_id). Un evento de tabla que no se pudo escribir se reintenta al final.

Raises:

Type Description
DumpError

Si falla el análisis inicial de carga (introspección de tablas de origen/destino) — un fallo no recuperable de orquestación, a diferencia de los fallos por tabla individual durante la carga (best-effort, reflejados en TableDumpResult.error_msg).
DumpReportError

Si falla la generación del informe Excel, ya terminada la carga. exc.result lleva el DumpResult completo (su report es la ruta prevista, sin crear).
OperationCancelledError

Si cancel_token se canceló (phase: "tables" o "rows").

plan() ¶

Vista previa del volcado sin escribir en el destino (G29 de util_bbdd_web, 4.4.0).

Lee lo mismo que el análisis de :meth:run (tablas de origen y destino y FK del origen, con el mismo orden topológico) y las columnas de las tablas con destino. No desactiva constraints, no limpia ni carga, no cuenta filas y no escribe informe ni auditoría. plan().load_order es el DumpResult.load_order que daría run() con el mismo catálogo.

Returns:

Type Description
DumpPlan

El plan: orden de carga, ciclos, tablas sin destino, columnas por tabla y avisos.

Raises:

Type Description
DumpError

Si falla la introspección de origen o destino.
Example

plan = DumpOrchestrator(config).plan() # doctest: +SKIP [w.code for w in plan.warnings] # doctest: +SKIP ['MISSING_TARGET']

bulk_audit_path OptionalPathField

Ruta (str o Path) del CSV de auditoría para los inserts en destino. None (default) = los inserts no se registran en auditoría.

 OptionalPathField()
collect_row_counts bool

Si True (default), se ejecutan COUNT(*) sobre origen y destino por tabla para obtener la volumetría real. False los omite y usa -1 como sentinel; útil en volcados de alto volumen donde el conteo es costoso (Snowflake, Oracle sin estadísticas actualizadas, tablas muy grandes).

 True
sync_pk_sequences bool

Si True (default), ejecuta la Fase 6a tras la carga: resincroniza los contadores PK (sequence / IDENTITY / AUTO_INCREMENT) en el destino para que coincidan con el MAX real de cada columna. Desactivar con False si se gestiona la resincronización manualmente o si el motor destino no soporta la operación con los permisos disponibles.

 True
commit_every_n_chunks int | None

Si se indica (entero ≥ 1), la carga de cada tabla commitea cada N lotes de chunk_size filas en lugar de en una única transacción por tabla, acotando el tamaño de la transacción (undo/redo log) en tablas muy grandes. None (default) = una transacción por tabla (atómico por tabla). Advertencia: con la cadencia activa la carga de una tabla deja de ser atómica; un fallo a mitad deja committeados los lotes anteriores de esa tabla (coherente con la semántica best-effort del volcado).

 None
manage_indexes bool | IndexMode

True o "secondary" (3.2.0, equivalentes): deshabilita los índices secundarios no únicos del destino antes de la carga y los reconstruye al final, acelerando los INSERT en tablas con muchos índices. False (default) = no se tocan los índices. Misma estrategia que BulkCrud.maintenance_scope(disable_indexes=...) (bulk/_support/secondary_indexes.py): mssql ALTER INDEX DISABLE→REBUILD (solo NONCLUSTERED), oracle UNUSABLE→REBUILD, postgresql DROP+recreate desde pg_get_indexdef, mariadb/mysql (desde 3.2.0) InnoDB DROP INDEX + un ALTER TABLE … ADD INDEX por tabla y MyISAM/Aria DISABLE KEYS (el DDL de lo que se borra se loguea antes). Nunca toca índices que respaldan PK/UNIQUE ni, en InnoDB, los que necesita una FK. Efecto medido a 3,5M filas con 2 índices secundarios (tras solapar lectura y escritura): Oracle −14 % (reconstrucción 2,7 s), SQL Server −8 %, PostgreSQL sin ganancia; en una carga directa con bulk la ganancia es mayor (sesión 2026-10-18b, G0). Compensa más cuantos más índices secundarios tenga el destino; no se activa automáticamente. "all" (3.3.0): además, índices únicos y PK/UNIQUE (nunca el índice clustered ni la PK de InnoDB o de una IOT), con las FK que los referencian (SQL Server y Oracle las reactivan; PostgreSQL las borra y recrea NOT VALID + VALIDATE). La unicidad no se comprueba durante la carga: solo para datos ya validados (p. ej. la carga final de un proceso con iteraciones de calidad). Exige truncate_target=True y no admite on_error="isolate" (los duplicados no darían error que apartar). Si un único no se puede reconstruir (duplicados), el resultado del índice es "failed" con las claves repetidas en error_msg.

 False
validate_fks_after bool

MariaDB/MySQL (3.3.0; por defecto desde 3.4.0): tras reactivar FOREIGN_KEY_CHECKS, comprueba con un NOT EXISTS por FK que no se cargaron filas huérfanas (constraint_results pasa de "unverified" a "enabled"/"failed"). En el resto de motores la validación ya se hace al reactivar. True (default desde 3.4.0); False deja la fila única "unverified" de hasta 3.3.0.

 True
max_parallel_tables int

Número máximo de tablas a cargar concurrentemente dentro de un mismo nivel topológico FK (tablas mutuamente independientes). 1 (default) = carga secuencial. Valores > 1 usan un ThreadPoolExecutor con una instancia BulkCrud por hilo. Las tablas en ciclos FK se cargan siempre secuencialmente. Se degrada automáticamente (con warning) a la capacidad real del pool de conexiones (pool_size + max_overflow) de origen/destino. La auditoría sigue activa bajo paralelismo: las escrituras de los hilos al mismo CSV se serializan con un lock por ruta.

 1
parallel_pk_ranges int | Literal['auto']

Número de rangos contiguos de PK en que particionar la carga de cada tabla con PK de una sola columna entera (WHERE pk >= lo AND pk < hi), cargados en paralelo con su propia BulkCrud. 1 (default) = sin particionado. Solo aplica a tablas cuya PK es una única columna entera presente en las columnas comunes; el resto se cargan completas. La concurrencia total (max_parallel_tables * parallel_pk_ranges) se degrada con warning a la capacidad real del pool. Requiere que el destino no tenga triggers per-fila dependientes del orden de inserción. Efecto medido con 4 rangos a 3,5M filas (frente a la carga secuencial, que ya solapa lectura y escritura): SQL Server −37 % (recomendado); PostgreSQL −9 % y Oracle −2 % (poca ganancia); MySQL y MariaDB casi el doble de tiempo (no recomendado; se avisa en el log); SQLite se fuerza a 1 (un solo escritor). "auto" (v3.0.0): el número de rangos de cada tabla lo decide ParallelPlanner con el motor de destino y las filas del origen (el COUNT(*) de collect_row_counts; sin él, la cota MAX(pk) − MIN(pk) + 1, que sobrestima si la PK tiene huecos), con las mediciones de arriba: hoy solo particiona con destino SQL Server y tablas de 3,5M filas o más (4 rangos, o menos si el pool no da para max_parallel_tables × 4); el resto se carga entera. El motivo de cada tabla queda en el log (INFO).

 1
write_batch_size int | None

Filas por lote de escritura en el destino (una sentencia COPY o executemany por lote). None (default): 20 000 con destino PostgreSQL (COPY, −31 % a 3,5M filas frente a 5 000) y chunk_size en el resto de motores (en SQL Server un lote de 20 000 fue un 81 % más lento). Con commit_every_n_chunks el default es siempre chunk_size, para no cambiar cada cuántas filas se confirma. Un entero fija el lote en todos los motores. La lectura sigue siendo por chunk_size; los chunks leídos se agrupan hasta completar el lote (+1 lote en memoria).

 None
on_error Literal['raise', 'isolate']

Como RejectOptions(on_error=...) de BulkCrud: con "isolate" las filas que el destino no admite (PK duplicada, NOT NULL, valor demasiado largo o fuera de precisión) se apartan a rejects_csv_path y el resto de la tabla se copia; la tabla queda success con TableDumpResult.rows_rejected. Durante la carga las constraints del destino están desactivadas: las FK y los CHECK no fallan aquí (una fila huérfana se copia y falla al rehabilitar la constraint, como sin aislamiento). La posición (fila) es la de la lectura del origen (SELECT sin ORDER BY: no se repite entre volcados); con parallel_pk_ranges es la del rango, que va en la columna particion. Fase 4, sesión 2026-10-01u.

 'raise'
rejects_csv_path OptionalPathField

CSV de rechazos común a todas las tablas (ver BulkCrud). Obligatorio con on_error="isolate".

 OptionalPathField()
max_rejects int | None

Filas que cada tabla (o cada rango, con parallel_pk_ranges) puede rechazar; la siguiente deja esa tabla en error y el volcado sigue. None (default): sin límite.

 None
bulk_audit_strict bool

Se pasa como audit_strict a cada BulkCrud y ParallelBulkLoader del volcado. False (default): un fallo al escribir el CSV de auditoría no interrumpe la carga; se registra como ERROR y se cuenta en DumpResult.audit_summary.audit_failures. True: el fallo deshace la carga de esa tabla (o partición) y queda como error de la tabla.

 False
audit_sink AuditSink | None

Destino opcional de eventos de auditoría (:mod:util_bbdd.audit, p. ej. JsonLinesAuditSink). Recibe los eventos operation de las BulkCrud del volcado y los partition/run de las cargas por rangos (con bulk_audit_strict como política de fallo de los operation), el evento table de cada tabla al terminar su carga (4.4.0; antes, al final) y, al terminar, uno por tabla sin destino, constraint, índice y contador PK, y un run de cierre. Todos llevan el mismo run_id (DumpResult.audit_run_id). Se puede usar sin bulk_audit_path. Un fallo al escribir estos eventos se registra como ERROR y no cambia el resultado (el evento de una tabla que falla se reintenta al final). None (default): sin eventos.

 None

Raises:

Type Description
ValueError

Si chunk_size no es un entero ≥ 1, o si commit_every_n_chunks o write_batch_size no son None ni un entero ≥ 1, o si on_error, rejects_csv_path y max_rejects no son una combinación válida (las reglas de BulkCrud), o si output_dir, bulk_audit_path o rejects_csv_path no son str ni Path, o parallel_pk_ranges no es un entero ni "auto". Se valida al construir, antes de tocar el destino.

DumpReporter¶

Genera el informe Excel de auditoría a partir del resultado del volcado.

DumpReporter(output_dir) ¶

Genera el informe Excel de auditoría de un volcado de datos.

Genera un único fichero .xlsx con 3 hojas fijas y hasta 5 opcionales:

  • Auditoría Tablas (fija): volumetría origen vs. destino por tabla, estado, y sección de constraints con incidencia si aplica.
  • Tablas Faltantes (fija): tablas del origen que no existen en destino.
  • Columnas Inexistentes (fija): columnas presentes en origen pero ausentes en destino (omitidas de la carga).
  • Índices (opcional): índices secundarios deshabilitados/reconstruidos.
  • Auditoría Bulk (opcional): resumen del CSV de auditoría y contadores del volcado.
  • Secuencias PK (opcional): sincronización de contadores de PK en destino.
  • Errores de Reactivación (opcional): fallo general al reactivar constraints. Solo aparece si constraint_reactivation_error != None.
  • Condiciones del motor (opcional): condiciones de ejecución de origen y destino (EngineReadinessAdvisor).

Las hojas opcionales se añaden siempre al final, para no mover las demás.

ConstraintManager¶

Gestiona la desactivación y reactivación de constraints en el motor destino.

ConstraintManager(engine, schema=None, *, validate_fks_after=True, journal_path=None) ¶

Gestiona la desactivación/reactivación de constraints en el motor destino.

Usar como context manager garantiza que enable_all() se llama incluso si la carga lanza una excepción. Los resultados quedan en constraint_results tras salir del bloque with.

Ejemplo::

mgr = ConstraintManager(target_engine, schema="dbo")
with mgr:
    mgr.disable_all(tables=load_order)
    # ... cargar datos ...
print(mgr.constraint_results)

disable_all(tables) ¶

Desactiva constraints en las tablas indicadas del motor destino.

Los fallos por constraint/tabla individual se degradan a warning (best-effort, ver los métodos _disable_*); un fallo real que impida desactivar constraints en absoluto (p.ej. conexión perdida a mitad de la operación) se relanza como DumpConstraintError en vez de propagar la excepción cruda de SQLAlchemy.

Con journal_path (SQL Server, PostgreSQL y Oracle), escribe el diario antes de desactivar la primera.

IndexActionResult¶

Resultado de gestionar (deshabilitar/reconstruir) un índice individual.

IndexActionResult(table_name, index_name, dialect, action, error_msg='') dataclass ¶

Resultado de gestionar (deshabilitar/reconstruir) un índice individual en el destino.

Lo devuelven dump.IndexManager (DumpResult.index_results), :meth:BulkCrud.maintenance_scope (MaintenanceScopeResult.index_results) y ParallelBulkLoader.load (ParallelLoadResult.index_results). Desde 3.2.0 vive en bulk; util_bbdd.dump.IndexActionResult es la misma clase.

Attributes:

Name Type Description
table_name str

Tabla a la que pertenece el índice ("*" para resultados globales).
index_name str

Nombre del índice ("*": toda la tabla, p. ej. DISABLE KEYS de MyISAM/Aria).
dialect str

Dialecto del motor destino.
action Literal['rebuilt', 'recreated', 'failed', 'unsupported', 'skipped']

Resultado de la operación:

  • "rebuilt" — índice deshabilitado/unusable y reconstruido (mssql/oracle; MyISAM/Aria ENABLE KEYS).
  • "recreated" — índice eliminado y recreado desde su DDL (postgresql; mariadb/mysql InnoDB).
  • "failed" — fallo al reconstruir/recrear; ver error_msg.
  • "unsupported" — motor no soportado (hasta 3.1.x, mariadb/mysql InnoDB en dump).
  • "skipped" — no se desactivó y se mantuvo durante la carga (desde 4.0.0: índice único de Oracle sin constraint cuyo DDL no se pudo obtener; el motivo, en error_msg).
error_msg str

Detalle del error cuando action="failed", "unsupported" o "skipped".
